# 决议讨论与取舍记录

本文按时间顺序记录 Iris 在关键节点的设计讨论、作者的核心考量、候选方案的利弊推演以及最终为什么这样取舍。  
结论速查表见 [DECISIONS.md](DECISIONS.md)，分层实现见 [ARCHITECTURE.md](ARCHITECTURE.md)。

---

## 2026-11-20 · 立项定位与五个架构单向门

### 核心想法
市面上本地播放器要么界面陈旧、配置繁琐，要么在照片广色域、大图翻页和启动速度上表现粗糙；跨平台套壳方案又往往牺牲原生性能。Iris 的初衷是做一个**解码与色彩管线极其扎实、启动即看、同时对视频与照片一视同仁**的跨平台（macOS + Windows）播放器。

### 关键取舍
1. **为什么坚持手写 `iris-mpv` + 原生下层合成，而不把视频帧塞进 GPUI 纹理？**
   - GPUI 0.2.2 的 `surface()` 仅接受 NV12 `CVPixelBuffer`，且让 UI 框架逐帧搬运视频纹理会引入额外拷贝与色彩损失。
   - 将视频放在 GPUI 透明视图下方的原生层（macOS `CAOpenGLLayer`、Windows 双 DirectComposition 目标），视频帧零拷贝直出，UI 静止时可以做到 `0 Hz` 空转，互不拖累。
2. **为什么不提前抽 `MediaBackend` trait？**
   - 只有一套 `libmpv` 实现时写抽象接口必猜错边界（例如未来照片走原生 ImageIO / WIC 图层时，替换的是视图层而非内核播放命令抽象）。坚持“等真正有第二套实现再提炼”。
3. **为什么选择路线 B（主程序 `MIT OR Apache-2.0` + 动态链接自建 LGPL 媒体库）？**
   - 保留未来商业化或闭源扩展的空间，同时严守开源合规底线：不碰静态链接，不用混入 GPL FFTW3 的官方预编译包，自行维护可复现源码构建与随包合规清单。
4. **为什么坚持会话挂在视口（`Viewport`）而非窗口（`Window`）？**
   - 同屏 A/B 对比审片是摄影与视频工作者的刚需。早期把会话挂在视口上几乎零额外成本，但若挂死在窗口上，后期改造成双视口将伤筋动骨。

## 2026-11-22 · 控制面插件架构与单版本正交协议

### 核心想法
播放器本体应当保持克制，不能把所有小众需求都塞进内核；但用户对构图辅助线、A-B 精听标记、云端媒体源和界面定制有真实诉求。需要一套既安全隔离、又不绑架特定脚本运行时的插件机制。

### 关键取舍
1. **像素管线内核独占 vs. 控制面开放**
   - 插件一旦触碰实时视频帧或解码管线，就会破坏硬件加速、広色域准确度与 60fps 稳定性。因此划定死线：**解码与色彩渲染由内核独占，插件只在控制面、矢量叠层与虚拟数据源层工作**。
2. **外部 JSON-lines stdio 子进程 vs. 内嵌 Lua / Wasm**
   - 内嵌脚本引擎会增加二进制体积、绑定单一语言生态并带来进程内崩溃风险。采用 JSON-lines stdio 协议（`PROTOCOL_VERSION = 1`），外部插件可用任意语言或独立二进制编写，子进程卡死或崩溃绝不拖垮播放器主进程；同时内置轻量官方插件通过 Rust `BuiltinPlugin` trait 零进程运行。

## 2026-11-22 · 中期方向校准：本体一致与插件自由度、工作区预设、远程协议全插件化

### 背景
随着虚拟数据源、工作区预设、快捷键方案与插件控件树快速落地，代码规模突破四万行并出现十余个超千行大文件，同时暴露出“方向 C 严苛约束与插件定制能力冲突”、“预设全量覆盖误伤用户配置”、“WebDAV 在内核与插件之外形成第三套平行分支”等问题，需要进行一次系统性的中期方向校准与工程重构。

### 决议一：本体默认视觉保持方向 C 一致，但给插件留出较大自由度
- **核心想法**：方向 C“模块面板”（石墨底色、极细边框、`#FF5B1F` 信号橙、硬朗直角）解决的是**播放器本体的审美统一性与开箱品质感**，而不应该成为束缚插件创作者的紧箍咒。如果把插件锁死在不能改圆角、不能改栏高、不能做无标题栏影院窗，插件生态就会失去生命力。
- **面临的坑点**：放开 `hide_titlebar` 与动态尺寸后，若宿主缺少兜底，插件隐藏标题栏会让窗口既无关闭按钮又无法用鼠标拖动（变成“死砖”），配错颜色还会导致设置面板看不见字而无法关掉插件；业务代码里到处手写圆角判断也会污染 UI 代码。
- **最终取舍**：**不阉割插件的 `UiThemeSpec` 与 `ChromeLayoutSpec` 自由度，改由宿主建立三道安全护栏 + 令牌层收口**：
  1. 开启 `hide_titlebar` 时，鼠标移至窗口顶缘自动以 `absolute()` 叠层浮现半透明标题栏（不参与 Flex 排布，避免视频画面跳动），视口支持 `Alt/⌘ + 拖拽` 及未缩放态阈值拖拽移动窗口；
  2. 命令面板与系统原生菜单常驻「恢复默认外观」逃生动作，宿主在令牌解析层强制兜底文字与背景最小对比度；
  3. 动态圆角与栏高在 `ThemeTokens` 中预计算并收口进 `ui/kit` 基础控件，业务页面保持干净。

### 决议二：工作区预设采用“带个人基线保护与自动回退的稀疏场景宏”（`1B+`）
- **核心想法**：当插件拥有较大界面与功能自由度后，用户在不同场景下（日常看片、沉浸观影、构图线审片、AB 循环 + 短步长精听学习）需要一键切换整套“布局 + 播放策略 + 插件组合”，这就是设计工作区预设的初衷。
- **三种候选方案的权衡**：
  - *候选 A（纯布局预设）*：最简单，但无法联动切换 `3s` 精听步长或自动开关构图线/AB 循环插件，丢失了多维工作区联动的价值。
  - *候选 C（基线 + 内存覆盖层 Session Overlay）*：虽然退出预设可还原基线，但有两个硬伤——① 激活预设期间用户在设置页拨动被遮罩覆盖的开关时，要么界面无反应（改了底层却被遮住），要么重启丢失，心智极其拧巴；② 预设发出的插件命令已改写插件自身状态，退出遮罩时宿主无法自动帮插件回滚，导致“半回滚”割裂。
  - *候选 B（稀疏增量宏 Sparse Patch + Apply-Once）*：把所有字段改为 `Option<T>` 稀疏补丁、把插件改为显式 `enable/disable` 差量（根除旧版全量覆盖无关设置、误启全部禁用插件的 Bug），保持全局单一 `Settings` 真源。但它原本有一个小遗憾：**“单向留痕”**——从设了 `3s` 步长的“精听”切到未设步长的小窗时，`3s` 会残留；若靠“默认工作区”写死 `5s` 回正，又会冲掉用户自己平时习惯的 `10s`。
- **最终取舍（`1B+` 方案）**：在稀疏增量宏基础上加入**“磁盘纯净个人基线 + 内存 `PresetRevert` 自动回退记录”**：
  - `settings.conf` 始终只持久化用户的个人日常基线与当前 `active_preset` ID（哪怕在特殊预设下崩溃退出，日常习惯也绝不丢失，冷启动读基线后再重放预设）；
  - 切换预设时先按内存 `PresetRevert` 自动还原上个预设改过的字段并执行 `on_exit` 插件指令（如离开审片自动关构图线），再打新预设补丁；运行期用户手动改某项设置则直接更新基线并从回退表移除。既保住完整多维自由度，又保持单层直读心智且零留痕。

### 决议三：本地内核只留通用网络底座，所有远程协议皆由插件实现（`R-Builtin+`）
- **核心想法**：远程存储（NAS、WebDAV、S3、Alist、媒体服、各类网盘）是核心场景，但如果每支持一种协议都往内核和 UI 里塞一套专属数据结构与弹窗，内核很快就会臃肿不堪。最彻底的架构是：**本地内核只提供通用的网络流传输与安全凭据能力，所有具体远程协议一律通过插件实现**。
- **推演与取舍**：
  1. **淘汰本地 `StreamGateway` 代理，直通 `libmpv`**：此前自建本地 HTTP 代理网关导致 HLS（`.m3u8`）相对分片失效且高频拖拽易触发连接上限报错。改为通过 `mpv_command_node_async` 结构化安全传参（单文件 `http-header-fields-append`，零注入风险）直交 `libmpv` 原生网络栈；同时**允许插件返回 `http://127.0.0.1:<port>` 本地回环地址**，使未来第三方编写 SMBv3、SFTP 或私有加密网盘插件时可在插件子进程内自建微型流桥接，内核无需链接任何额外协议 C 库即可通吃一切协议。
     - 后续安全审计发现直连会跳过宿主的地址和重定向检查。当前实现通过每个播放会话独立的 `PlaybackRelay` 打开全部 HTTP(S) 流，转发时处理 HLS 相对资源、同源凭据和取消操作。插件仍可使用自身的高端口回环桥接服务。
  2. **补齐 `iris-api` 多实例数据源能力**：新增动态 `SetSources` 与连接增删改事件、弹窗异步校验 Pending 闭环及 `2 MiB` 管道单行上限，彻底删除内核与 UI 中 165 处硬编码 WebDAV 分支，`MediaUri` 精简为 `Local | HttpUrl | Plugin` 三元模型。
  3. **官方 WebDAV 的交付形态取舍（内嵌标准插件 vs. 随包独立二进制 vs. 外部另装）**：
     - Windows 裸机默认没有 Python（且存在系统商店假 `python.exe` 拦截），若只把 WebDAV 做成外部脚本会导致普通用户开箱无法连 NAS；若做成独立子二进制又会增加双端签名公证与进程冷启动负担。
     - 因此选择 **`R-Builtin+`**：将官方 WebDAV 严格按标准 `iris-api` 插件协议编写为编译期内嵌插件 `iris.webdav`（配后台线程异步回包通道 `PluginSink` 保证慢速 NAS 绝不卡主线程）。内核与 UI 对它零特权、零后门；用户可在插件面板一键禁用；同时锁定 `iris.*` 命名空间并将 Keychain 凭据按 `builtin.*` / `ext.*` 物理隔离，既保障双端单文件开箱即用，又允许随时禁用并换用第三方增强插件。

### 决议四：拒绝机械切碎文件，立下先收敛再拆分与硬门禁纪律
- 面对 12 个超千行文件，拒绝“把 3000 行意大利面条机械切成 6 个 500 行碎面条”：先通过统一 `CatalogItem` + 独立 `PlayQueue` + 共用 `ui/kit` 原语消除约四成重复代码，将 `IrisWindow` 收敛为 6 个粗粒度正交领域状态块，再拆分子模块并在 `check-project.py` 中用 **650 行软警告 / 1000 行生产代码硬阻断** 锁死模块规模，防止腐化复发。

当前门禁为超过 650 行生产代码提示、超过 850 行生产代码或 1,000 总行数阻断。

## 3. 五个“单向门”

| # | 结论 | 状态 |
|---|---|---|
| 3.1 | **会话挂在视口上，不挂在窗口上**：同屏对比两张图 / 两段视频，是一个窗口里两个视口、两个 mpv 实例、两个原生视频层。数据结构按“窗口持有 `Vec<Viewport>`”组织，MVP 里长度固定为 1，布局测量按视口同步矩形。 | 计划（现在只有一个视频区）|
| 3.2 | **上下文驱动的输入**：不在 UI 里到处写 `if is_photo`。见下方 3.2 细则。 | 计划 |
| 3.3 | **许可走路线 B**（宽松协议，保留商业 / 闭源扩展可能）。见第 5 节。 | 方向已定，具体协议待决 |
| 3.4 | **媒体只读 + 路径做主键**：内核对媒体文件和目录永远只读，个人数据放应用数据目录。收藏、进度等记录用路径做主键；内容指纹只用来在文件移动后重新匹配，而且只在真要写记录时才对那一个文件计算，打开目录时不读文件内容。 | 只读已遵守；记录功能尚未开始 |
| 3.5 | **色彩准确是内核的硬指标**：视频层要做色彩管理，见第 6 节。 | 进行中 |

### 3.2 输入上下文细则

- 上下文分层：`Workspace`（全局）→ `Viewport`（视口共性）+ 状态标签 `media=video|image|none`、`zoomed` → 最高层的 `Tool` / `Overlay` / `Sidebar`（目录栏聚焦，以及未来插件的 `tool=crop` 之类）。
- 上下文由当前状态在 `render()` 里纯函数推导，不手动 `set_mode`。
- GPUI 的 `KeyBinding` 只管键盘。滚轮、拖拽、双击要另写一个同样按上下文匹配的 `resolve_pointer_input(event, modifiers, context) -> Option<Command>`。
- 侧栏和全屏工具栏要阻断滚轮和点击冒泡，避免在目录里滚动时底下的图片跟着缩放。
- 动作按意图命名，不按按键命名（`ZoomIn`、`SeekForwardExact`、`OpenNextMedia`……），视频专属、看图专属和共用动作分开。
- 跨平台快捷键用 GPUI 的 `secondary-*` 修饰符（macOS 是 ⌘，Windows 是 Ctrl）。已改为 `secondary-o` / `secondary-q`，空窗口的提示文字按平台显示 ⌘O 或 Ctrl+O。
- 复核补充的约束：
  - GPUI 0.2.2 **没有**双指捏合（magnify）事件。要做捏合缩放，只能自己在 NSView 上接 `magnifyWithEvent:`，或先不做。
  - `start_window_move()` 在 macOS / Windows 上是空函数，窗口拖动继续用 `platform.rs` 自己的实现。
  - **焦点纪律**：GPUI 会在空格或回车松开时，对获得焦点的元素触发 click。所以工具栏、标题栏的按钮点击后不保留键盘焦点，焦点始终回到视口；只有文本输入框才拿焦点。否则“点完静音按空格又静音”。
  - 看图时空格切换“适应窗口 / 1:1”这类绑定，必须在焦点纪律定下之后再加。

## 5. 许可：路线 B

用户已选路线 B：主程序用宽松协议，保留以后出商业版或闭源插件的可能。落地要求：

| # | 结论 | 状态 |
|---|---|---|
| 5.1 | 主仓库协议定为 Apache-2.0 或 `MIT OR Apache-2.0`，补 `LICENSE` 文件。GPUI 是单一 Apache-2.0。 | **待决**：选哪一个；目前 `Cargo.toml` 仍是 `UNLICENSED` |
| 5.2 | 分发用的 libmpv / FFmpeg 必须**自己从源码构建成 LGPL-2.1 版**：FFmpeg 不加 `--enable-gpl`、`--enable-version3`、`--enable-nonfree`；mpv 用 `-Dgpl=false -Dlibmpv=true -Dcplayer=false`。放在单独的构建仓库，用 CI 产出。 | 计划（首次对外发包前）|
| 5.3 | **不用 mpv 官方的 LGPL 预编译包**：mpv discussion #18595 里维护者明确说唯一安全的做法是自己从源码构建；而且官方 LGPL 包启用了 Chromaprint 并配 FFTW3，**FFTW 是 GPL**。自建时要确认关掉 Chromaprint 或不链 FFTW。 | 已定 |
| 5.4 | Homebrew 的 libmpv 是 GPL 构建，**只能开发时用**，不能拿去分发。 | 已定 |
| 5.5 | 只能动态链接：macOS 放 `Iris.app/Contents/Frameworks/*.dylib`，Windows 放主程序同级 `*.dll`。绝不静态链进 `iris`。 | 已遵守（现在就是动态链接）|
| 5.6 | 每次产出 libmpv 时，把本次构建用到的全部 C 库源码一起打包发布（对应源码义务由分发者本人承担）。 | 计划 |
| 5.7 | `deny.toml` 看守 Rust 依赖的许可证。 | 已完成（见 2.12）|
| 5.8 | 维护两套平台的 LGPL 构建流水线是**持续成本**，要计入里程碑。 | 已记录 |
| 5.9 | 宽松协议本身**不保证**“只有我能出商业版”：它同样允许别人闭源 fork。真想保留独家商业权，要考虑的是版权归属或 CLA，不是选哪个协议。 | 待决（是否需要 CLA）|

## 7. 照片走 mpv 的修补

实测数据见 TESTING.md。MVP 阶段看图继续用 mpv，但补以下几处：

| # | 问题 | 做法 | 状态 |
|---|---|---|---|
| 7.1 | 视频层没有色彩管理 | 见 6.2 | 已完成 |
| 7.2 | HEIC 的方向被忽略，竖拍照片横着显示 | 自己读出 HEIF 的 `irot` / `imir`。`video-rotate` 对分块 HEIC 无效，改用 `vf=format=rotate=…`（GPU 旋转），镜像用 `hflip` / `vflip` | 已完成（`photo.rs`）|
| 7.3 | 超过 16384 像素的图蓝屏、着色器报错 | 长边超过 8192 的图先经 `vf=scale` 在 CPU 上缩小再交给 mpv（12000² 在 16384 以内也报帧缓冲错误，所以上限取 8192） | 已完成（`photo.rs`）|
| 7.4 | 照片内嵌 ICC 被忽略 | 见 6.3 | 已完成 |
| 7.5 | 翻页慢（HEIC 约 300 ms）、无法预解码 | 修补不了，留给原生照片管线（6.6） | 已记录 |

## 8. 被复核否定的说法（不是共识）

| # | 讨论稿的说法 | 复核结论 |
|---|---|---|
| 8.1 | D3D11 渲染要设 `MPV_RENDER_PARAM_BACKEND = "gpu-next"`，且 libplacebo ≥ 7.387 | `render.h` 没有 BACKEND 参数，是编的。真正要注意的是不恢复设备状态、不能用 SINGLETHREADED。|
| 8.2 | 用 GPUI 的 `window.start_window_move()` 拖窗口 | 0.2.2 在 macOS / Windows 上是空函数。|
| 8.3 | 视口层支持双指捏合缩放 | GPUI 0.2.2 没有 magnify 事件。|
| 8.4 | 立刻从 cocoa / objc 迁到 objc2 | GPUI 0.2.2 自己用旧库，迁移后类型不互通；不是 MVP 的事。|
| 8.5 | `deny.toml` 只放行 MIT / Apache / BSD / ISC / Zlib / Unicode | 现有依赖树会直接报红，必须加 MPL-2.0 等。|
| 8.6 | 用 `target-colorspace-hint` 透传 HDR 和色彩空间 | render API 下管不到 Iris 的图层。|
| 8.7 | IINA 漏洞编号是 CVE-2026-5433 | 那是 Honeywell 工控模块的漏洞。IINA 的是 CVE-2026-47114。漏洞内容本身说对了。|
| 8.8 | `MediaId` 用“文件大小 + 头尾各 64 KB 哈希”做主键，“不到 0.1 ms” | 只在 SSD 且已缓存时成立；改 EXIF 或旋转照片 ID 就变。改为路径主键（3.4）。|
| 8.9 | 内核里定义 `MediaBackend` trait | 抽象层级不对：以后图片不走 mpv 时，要换的是底层画面层，不是内核里的后端接口。不写假想的接口。|
| 8.10 | 一个窗口对应一个会话 | 应挂在视口上（3.1）。|
| 8.11 | 打包用 `codesign --deep -s -` | 只是本机自签名，过不了 Gatekeeper，Apple 也不推荐 `--deep`。分发要 Developer ID 签名、开 hardened runtime、逐个签 dylib、公证。|
| 8.12 | “Windows 方案有 90% 以上把握” | 是估出来的数字。缩放不同步只能上机验证（ARCHITECTURE.md 第 4 节）。|
| 8.13 | 放弃 Intel Mac、最低 Win10 1903、商业模式走 Open-Core | 这是讨论稿替用户做的决定，**没有拍板**，列入待决。|
| 8.14 | 长期照片用系统解码后当 GPUI 纹理上屏 | GPUI 图片元素是 8 位 sRGB、无色彩管理。应改用原生图层（6.6）。|
| 8.15 | 把滤镜栈仲裁、插件插槽、命令面板、HDR/ICC、反向逐帧都列进内核的五个模块 | 和“现在不写插件代码”自相矛盾。MVP 不做这些。|

## 10. 待决问题

- **许可证**：Apache-2.0 还是 `MIT OR Apache-2.0`；是否需要 CLA 或版权归属安排（5.9）。
- **Windows 测试机**：有没有可用的 Windows 机器或云主机。Windows 小验证（4.4）卡在这里。
- **平台范围**：是否支持 Intel Mac（决定 libmpv 要不要编 universal 版）；最低 macOS 版本；最低 Windows 版本。
- **商业模式**：是否走 Open-Core。
- **MVP 验收清单**：确认或修改第 9 节。
- **Windows 单实例和文件关联**：macOS 双击文件默认发给已运行的进程，Windows 默认拉起新进程。
- **跨显示器**：窗口移到另一块屏幕时刷新率和色彩配置的变化（macOS 色彩部分已由当前方案处理，刷新率未看）。
- **调试管道收紧**：`mpv <命令…>` 和整个 `IRIS_CONTROL` 怎么限定在调试场景（编译特性、仅 debug 构建，或发布版去掉 `mpv` 命令）。实测脚本目前依赖 release 构建里的管道。
- **未复现的问题**：一次全新启动后先开图片，视频区是黑的，之后多次重启没再出现。
